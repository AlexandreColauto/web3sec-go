## 1. What the defect was

`environmentValue` (the `environment.network_access` field of every EXEC record) and
`Preview` (the dry-run surface) both read `profileNetwork[profile]` directly. That map
declares the *container* network flag (`none` / `bridge-host-gateway`), so every host
profile — `host-readonly`, `halmos`, `forge-fuzz`, `minicertora` — was recorded as
`network_access: "none"` while the process actually had the host's full network.
The r36 F5 fix had already made the *filesystem* label honest for exactly these
profiles (`profileFilesystemLabel`); the network half was left claiming isolation it
does not have.

## 5. Why `assets/schema/sandbox_execution.schema.json` had to change

`validation.WriteJson` validates before writing (`internal/validation/atomicio.go:34-39`),
and `internal/sandbox/exec.go` writes every EXEC record with
`validation.WriteJson(path, record, "sandbox_execution")` (lines 725, 739, 791, 1245).
The record's `environment.network_access` enum was
`["none", "fork-rpc-only", "bridge-host-gateway", "full"]`, so the honest label made
**every host-profile record write fail** — `Sandbox.Run` returned the schema error and
`execDirTxn` unwound the exec dir (red #3). `internal/audit/sections/execs.go:29`
independently validates stored records against the same schema.

This is exactly the precedent the plan's Global Constraints point at: the r36 F5 commit
(`9641c681`) widened the same schema's `filesystem` enum for the *filesystem* honest label
and resynced the manifest — its commit body says verbatim "Schema change required an asset
manifest resync." Task 2 is the network twin of that fix, so it widens the network half the
same way:

```diff
-        "network_access": { "enum": ["none", "fork-rpc-only", "bridge-host-gateway", "full"] },
+        "network_access": { "enum": ["none", "fork-rpc-only", "bridge-host-gateway", "full", "host (unconfined — nothing enforces network-off)"] },
```

and regenerates the manifest (`python3 scripts/sync-asset-manifest.py`, exit 0, "130 files
in 9 packs"); `assets/manifest_test.go` pins the schema bytes, so a stale manifest would
fail the full gate:

```diff
    "sandbox_execution.schema.json": {
-    "sha256": "00ecd581800e27624828a195e436f045fd28cb9e1acbab16d6a9a08b8411f0df",
-    "size": 5171
+    "sha256": "0a22d3ee1d039e8195499cc04d26e9f293edfbf7c8c7d17fe525623c4a5e5384",
+    "size": 5225
    },
```

No other schema change was needed: `container.network` keeps its
`["none", "bridge-host-gateway"]` enum (host profiles carry `container: null`), and
`Preview`'s output is not a schema-validated artifact.

## 6. Every updated test expectation

The brief predicted that existing tests pinning `"none"` for host profiles would fail. That
is half true, and the honest account is:

1. **The tests that actually failed were the 13 in red #3** — not because they assert
   `"none"`, but because the schema refused the record write outright. No test anywhere
   asserted a host-profile *record's* `network_access == "none"`; the only such assertions
   (`internal/sandbox/ext_test.go:367`, `internal/sandbox/sweep_t35_test.go:87`) run the
   `docker-networkless` container profile, whose label is unchanged.

2. **Two existing pins did read the raw map for host profiles and were updated anyway**
   (the brief's instruction — they pin the profile's network posture, and that posture is
   now honest only through `networkLabel`). Both are in `internal/sandbox/exec_test.go`:

   | Test | Before | After |
   | --- | --- | --- |
   | `TestHostProfilesAreHostOnly` (was line 84) | `if network := profileNetwork["halmos"]; network != "none" { t.Errorf("halmos network = %q, want none", network) }` | `if network := networkLabel("halmos"); !strings.Contains(network, "unconfined") { t.Errorf("halmos network = %q, want an unconfined-host disclosure (a host run has the host's network)", network) }` |

   These two pins read the map directly, so they passed both before and after — they were

## 9. Concerns

1. **The brief's file list was incomplete (the one real deviation).** Task 2 names
   `profiles.go`, `exec.go`, `exec_test.go` — but the honest label *cannot ship* without the
   `assets/schema/sandbox_execution.schema.json` enum widening plus the manifest resync,
   because `WriteJson` validates before writing and refuses every host-profile record
   (proven by red #3: 13 tests, `Sandbox.Run` failing for all host profiles). Both extra
   files are task-owned and are staged by exact path. The plan's Global Constraints call the
   asset manifest out of bounds as a *pre-existing operator modification*; in this worktree
   `git status` was clean, so this manifest diff is new, task-caused, and required by
   `assets/manifest_test.go`. Precedent: r36 F5 did exactly this pair of edits.
2. **`networkLabel` placement.** The plan is internally contradictory: its Files list says
   "Modify `internal/sandbox/profiles.go` (add one helper near `profileFilesystemLabel`'s
   twin in exec.go — keep both label helpers adjacent)" while Step 3 says "add
   `networkLabel` next to `profileFilesystemLabel`" (which lives in `exec.go`). The
   orchestrator's brief resolved it to `profiles.go` "near the profile maps", which is what
   was done (`profileFilesystemLabel` itself is in `exec.go`, so the two helpers are not
   textually adjacent). Functionally irrelevant (same package); flagging so a reviewer does
   not read it as drift.
3. **Stale prose in docs (NOT fixed — out of scope by instruction).** Three docs still tell
   the operator that a host profile is `network none`:
   `assets/runbook/RUNBOOK.md:67` ("network `none`, host-classified"),
   `docs/MINICERTORA_INTEGRATION.md:18`, `docs/MINICERTORA_ARCHITECTURE.md:79`. r36 F5
   corrected the RUNBOOK when it fixed the filesystem label; the equivalent one-line doc fix
   for the network label belongs to whoever owns docs — I was told to stage only this task's
   files and not to touch docs, so I left them. **This is the main reason for the
   DONE_WITH_CONCERNS status.**
4. **User-visible CLI change, unpinned.** `webv2 exec --profile halmos|forge-fuzz|minicertora
   --dry-run` now prints a 52-character label on its `network:` line. No test or golden pin
   covers it (verified by grep + full suite), but a downstream consumer that parses that line
   as an enum (`none`/`bridge-host-gateway`) would see a new value. The audit/schema side is
   handled (§5); the CLI printer was deliberately not touched — narrowing the printed label
   would re-introduce the dishonesty this task removes.
5. **`vm-snapshot` and `docker-gvisor` labels are unchanged and unverified.** They are
   container/VM profiles in `profileNetwork` with `"none"`, and `HostProfile` excludes them,
   so they keep `"none"`. I did not verify that a `vm-snapshot` run truly has no network
   (no VM runtime on this box); that is outside this task's law but worth a follow-up.
6. **`profileNetwork` is now referenced only by `networkLabel`** (plus its declaration). A
   future reader who reaches for the map directly for a record label re-opens this defect;
   the corrected doc comment says so, but nothing enforces it. A lint-level guard (e.g. the
   map being unexported and used only in `networkLabel`) is already true — the residual risk
   is a *new* call site in this package.
