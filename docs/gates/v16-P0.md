### 3. The coarse score, from the real scorer

The gold file is built from the project's 7 `high` rows in the scorer's own
required object shape (`gold_findings` + `scoring`), with
`gold_id = the dataset's finding_id` — exactly as the plan prescribes, because
`eval-gold`'s hard-coded `PASS_GOLD_ID "G-01"` cannot be a ScaBench id.

```
$ python3 scripts/eval-gold.py --gold "$WEBV2_P0_DIR/gold-<pid>.json" \
      --campaign "$WEBV2_P0_DIR/root/campaigns/C-a7844c6d23" > "$WEBV2_P0_DIR/score.json"
$ cat "$WEBV2_P0_DIR/score.json"
{"found": [], "missed": ["2024.09.13 - Final - Perennial V2 Update 3 Audit Report_H-01",
 "..._H-02", "..._H-03", "..._H-04", "..._H-05", "..._H-06", "..._H-07"],
 "false_positives": 0, "pass": false, "bonus": false, "verdict": "FAIL",
 "verdict_note": "", "operator_confirmed": {}}
```

`verdict: FAIL` is **by construction** and is not a finding about the tooling:
the campaign holds no findings at all (no agent was run against the target),
and the `G-01`/`G-02` pass/bonus concept does not transfer to a ScaBench
finding id. The measurement that matters is `found`/`missed`.

### 5. What did NOT run, and why

- **ScaBench's own baseline runner — NOT RUN.** `baseline-runner/baseline_runner.py`
  requires `--source` and an LLM (`pip install -r requirements.txt`,
  `OPENAI_API_KEY`). `OPENAI_API_KEY` is not set in this environment, so the
  runner half was skipped rather than faked. **Target status: `PINNED, RUNNER
  NOT RUN — no OPENAI_API_KEY`.**
- **The Nethermind judge arm (`scabench-judge`) — NOT RUN.** It needs
  `pip install "git+https://github.com/NethermindEth/auditagent-scoring-algo"`,
  `OPENAI_API_KEY`, per-project truth files and renamed result files. Same
  blocker. The `regress run --scorer scabench-judge` path itself is covered by
  unit tests (`TestRecordRunRecordsATranscribedJudgeScore`), which is not the
  same as a real judge run and is not claimed as one.
- **Network-free cross-check that WAS available:** ScaBench ships a
  pre-computed GPT-5 baseline for this project,
  `datasets/curated-2025-08-18/baseline-results/baseline_sherlock_20240913---final---perennial-v2-update-3-audit-report_2024_09.json`
  (6.5 KB; `total_findings: 5`, `files_analyzed: 4`, timestamp
  `2025-09-02T06:53:52`). It confirms the target is one the dataset's own
  pipeline actually runs on, but it is **not** a score for our campaign and is
  not compared to `found`/`missed` here.

### 6. What this section does not prove

- One target, not the suite. Suite selection, mirrors, answer keys and the
  stratification are Tasks 4, 5, 7 and 10.
- No detection was measured: `found: 0` is a campaign with no findings, so this
  proves the *records and the read-back*, not the tool's rediscovery rate.
  `is_detection_rate: false` on the run record is the same statement in machine
  form.
- The shape `lending-liquidation` is Task 1's provisional assignment; the
  derived label map (Task 3) may reassign it.
