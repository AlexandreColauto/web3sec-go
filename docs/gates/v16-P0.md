### 5. What did NOT run, and why

- **ScaBench's own baseline runner — NOT RUN.** `baseline-runner/baseline_runner.py`
  requires `--source` and an LLM (`pip install -r requirements.txt`,
  `OPENAI_API_KEY`). `OPENAI_API_KEY` is not set in this environment, so the
  runner half was skipped rather than faked. **Target status: `PINNED, RUNNER
  NOT RUN — no OPENAI_API_KEY`.**
- **The Nethermind judge arm (`scabench-judge`) — NOT RUN.** It needs
  `pip install "git+https://github.com/NethermindEth/auditagent-scoring-algo"`,
  `OPENAI_API_KEY`, per-project truth files and renamed result files. Same
  blocker. The `regress run --scorer scabench-judge` path itself is covered by
  unit tests (`TestRecordRunRecordsATranscribedJudgeScore`), which is not the
  same as a real judge run and is not claimed as one.
- **Network-free cross-check that WAS available:** ScaBench ships a
  pre-computed GPT-5 baseline for this project,
  `datasets/curated-2025-08-18/baseline-results/baseline_sherlock_20240913---final---perennial-v2-update-3-audit-report_2024_09.json`
  (6.5 KB; `total_findings: 5`, `files_analyzed: 4`, timestamp
  `2025-09-02T06:53:52`). It confirms the target is one the dataset's own
  pipeline actually runs on, but it is **not** a score for our campaign and is
  not compared to `found`/`missed` here.

### 5. The unweighted alternative — and §3a's weighting claim, measured

Three readings of "unweighted", all computed over the committed label file and the same shape map (§2), none of them by editing the label file:

| reading | what it picks | classes | `covered_findings` | gold findings the six carry |
|---|---|---|---|---|
| **the same greedy, gain = number of uncovered classes** (the apples-to-apples alternative) | **the identical six** (slots 4 and 5 swap) | 8 | 40 | 18 |
| **six biggest by gold count** (Mantra DEX 12, Cork 11, Coded Estate 9, Oku 8, BakerFi 7, Perennial 7) | the six largest projects | 8 | 46 | **54** |
| **random six** (20 000 draws) | — | — | — | mean 22.1 |

So on this snapshot **the weighting changes nothing that matters**: with the shape constraint in force, the weighted greedy and the class-count greedy produce the same six projects, the same 8 classes and the same 40 covered findings. The one difference is the ORDER of two slots — weighted pass 1 takes Starknet Perpetual in slot 4 (its uncovered `liveness` weighs 4) where the unweighted pass 1 takes Initia (both add one class, so the name tie-break decides), and pass 2 then takes the other — which is why the row above says "slots 4 and 5 swap" rather than "identical pick order". Unstratified, the weighting does move the pick — over all 31 projects the weighted greedy covers 49 of the classified findings against the unweighted greedy's 47, with 11 classes either way — but it buys weighted coverage, never class coverage. The precise claim is a **per-step** one, not a theorem about outcomes: at any single greedy state, the weighted argmax over that state's uncovered classes can never add more NEW classes than the unweighted argmax over the SAME state, because the gain is a sum of class weights, so a heavier class outranks a rarer one and a step that adds no class can outrank a step that adds one. What the final pick looks like is the accumulation of those steps, and the measured equality above is a property of THIS snapshot, not a general result. §3a's framing that the pick's justification is class coverage per checkout is therefore **not** what the weight implements; the four-shape constraint is what buys breadth, and the weight only decides which project fills each shape's slot.

Against the six biggest, the argued pick trades **36 of the 54 gold findings** (18 vs 54) for **no extra class at all** (8 vs 8) and six *fewer* covered findings (40 vs 46). That is the honest size of the class-coverage-per-checkout argument on this input, and after the §2 correction it is thinner than the first issue claimed (which had one extra class): on this snapshot the argued pick's only measurable advantage over "the six biggest" is the four-shape stratification — which is a real one, since the six biggest are unstratified and shape coverage is the composition constraint — and not class breadth. It is thin because 62 of the 114 gold findings are unmapped, so no pick can reach them, and because the six biggest already cover 8 of the 14 classes.

The plan's synthetic fixture does not rescue the claim either: on it the weighted and unweighted greedy pick *different* projects (weighted takes `filler-21`, a one-finding project that inherits its class's total weight; unweighted takes `big-c`, the twenty-finding project that carries those findings) yet cover the same six classes and the same 104 of 114 findings. That is pinned as a test (`TestSelectDropsTheRareClassAndPinsCoverage`), so the measurement is re-derivable rather than asserted.

### 6. The input's fitness — where the known-unfit caveat is recorded

The plan's selection schema has provenance for *which* input (`dataset` + `snapshot_date`) and none for how fit that input is, so the field was added: `input_class_fitness`, a string the selector writes into every selection it produces, carrying the Task 3 review's verdict verbatim in effect — 29 of 52 classified rows wrong; no `upgrade-initializer` row (20) and no `flash-loan` row (1) is defensible; those two artifact classes carry 21 of the 40 covered findings; coverage is a lower bound. The selection file above therefore says, in its own bytes, that its classes are known-unfit and points at §4 of this record for the row-by-row evidence. **It is a REQUIRED property of `regression_selection.schema.json`, not an optional one**: a hand-written or future selection that omits it is refused by `validation.Validate`, so the caveat cannot be dropped from a record by simply not writing it (a test pins exactly that, and the mutation that removes it from `required` turns the test red).

This matters for the picks above, not just in principle: `code4rena_next-generation_2025_05` (slot 3) contributes exactly one class, `upgrade-initializer`, which is one of the two classes with **no row the review would defend** — and it is in the suite because it is the only shaped bridge, not because its class is real. `sherlock_idle-finance_2024_12` and `code4rena_initia-move_2025_04` each contribute an `upgrade-initializer` row too, and BakerFi contributes the file's single `flash-loan` row. Read the covered-class count as "classes the suite exercises", never as "classes the snapshot has".

**The pick is not artifact-driven.** Re-running BOTH greedies (weighted and
class-count) with the `upgrade-initializer` class neutralized to `unmapped` —
i.e. with the largest artifact class deleted from the input rather than merely
discounted — selects **the same six projects** in both readings. Coverage falls
from 40 of 114 to 20 of 114 and from 8 of 14 classes to 7 of 13, because that
class held 20 of the 40 covered findings and 20 of the file's rows; what does
not move is the pick. So the suite's composition is not an artifact of the
matcher's biggest error: remove the error and the same six projects are still
the argmax, and `upgrade-initializer` is covered because the projects that
carry it are selected for other reasons (BakerFi for access-control and
flash-loan, Initia for oracle-manipulation, Idle Finance for
share-price-inflation), not the other way round.

### 7. Defects in the plan's Task 4, reported rather than papered over

1. **Step 2's test cannot pass against Step 4's code.** `TestSelectCoversTheRareClassAndAllFourShapes` asserts (a) the rare class `oracle-manipulation` is covered and (b) two held-out picks. On the fixture as written the greedy picks `{big-a, filler-21, filler-02, filler-03, filler-01, filler-04}`: `oracle-manipulation` (weight 3) loses every slot to a class of weight 4, and of the named held-out pair only `filler-01` is picked, so `Select` returns `1 of the 2 held-out projects were picked`. Both assertions were rewritten to what the algorithm actually does, and the held-out pair moved to two projects the greedy selects.
2. **The rare-class claim is a category error.** "The rare class is exactly what the weighting exists to catch" cannot follow from a gain that sums class weights: maximizing a weight sum never increases the *count* of covered classes. The plan's own prose two paragraphs earlier says the opposite ("the weighting argument is about classes, not counts").
3. **Pass 1 could not select the real snapshot at all.** Pass 1 was gain-gated, so a shape whose only candidate's classes the earlier picks already covered was reported as `no project covers shape %q` — false, and fatal here: the one bridge-shaped project's only classified class is `upgrade-initializer`, which the vault pick covers first, so `Select` refused the whole snapshot. Pass 1 now treats the shape slot as the CONSTRAINT §3a says it is (`requireGain=false`); pass 2 keeps the positive-gain requirement, where it is an optimization. Without this change Step 6 could not run.
4. **`picks[].gold_findings` under-reported, and all-unmapped projects were not candidates at all.** `profile` `continue`d on an unmapped row BEFORE the candidate lookup, so (a) a candidate's reported gold count was its *classified* count, not its high count — on the shaped set, BakerFi's 7 printed as 3, Kinetiq's 3 as 1, Initia's 4 as 3, Starknet Perpetual's 2 as 1 — and (b) a shaped project whose rows are all unmapped never became a candidate: Cabal, Liquid RON and Telcoin (3 of the 12 shaped projects) were invisible to the pick and to the "fewer than the picks" guard. The label file is the snapshot's 114 high findings, unmapped included, so all of a project's rows now count and every shaped project is a candidate. **The claim this section made in its first issue — that the plan's profile "can emit `gold_findings=0`, which the schema forbids" — was wrong**: the candidate was created inside the mapped-row branch with `total++` on that same row, so every candidate it could report had `total >= 1`, and `minimum: 1` was unreachable from that path. The defect was real but its stated mechanism was not. The greedy itself is unaffected: it reads classes and weights, not the per-project total.
5. **Two smaller spec slips, adapted:** Step 2 asserts the refusal text `"held out"` while Step 4's message says `"holds out exactly 2"`; and Step 2's determinism test compared two runs without pinning the clock, which would have measured `created_at`'s microseconds rather than the selector (now pinned with `WEBV2_NOW`, the repo's seam).
6. **Step 5 does not mention the help surface.** Adding a repo-level action changes `regressUsage` and `regressHelp`, both of which are byte-pinned by tests (`regressUsageLiteral`, `regressHelpLiteral`); left alone, the help would have documented no `select` action and no `select` flags. Both constants and both literals were updated with the six new flags.
7. **Three reachable refusals and one optional caveat, found by the same review (implementation defects, not plan defects).** (a) `input_class_fitness` was not in the schema's `required` list, so a selection omitting it validated and its coverage read as coverage of real classes; it is required now, with a test that validates the selector's own record and then the same record with the field removed. (b) The shape-vocabulary refusal walked `spec.Shapes` — a Go map — and returned on the first invalid entry, so with two invalid shapes it named a random project and contradicted §9's determinism claim; it now collects every invalid entry and renders them sorted. (c) The pass-2 exhaustion refusal, the post-pick hold-out refusal and the CLI's non-string `--shapes` value were all reachable and untested; each now has a test that was mutation-checked (mutating the guard turns it red).

### 9. The algorithm, precisely (so the pick is re-derivable)

`regression.Select` (`internal/regression/select.go`):

- **The input read** (`profile`): every row of the label file is one gold finding, so it counts in the snapshot total and in its project's `gold_findings`; a row whose class is `unmapped` (or empty) counts there and nowhere else. Each non-unmapped class's TOTAL row count across the whole snapshot is that class's **weight**. Only projects named in the shape map are candidates.
- **Pass 1 — one pick per shape, in `ScaBenchShapes` order** (`vault-erc4626`, `lending-liquidation`, `bridge-messaging`, `non-rollup-l2-or-oracle`): take that shape's unchosen candidate with the highest gain. This is a CONSTRAINT, not an optimization: the slot is filled even when its best candidate adds no uncovered class. Only if the shape has no shaped project at all does `Select` refuse, naming the shape.
- **Pass 2 — fill the remaining slots**: take the unchosen candidate with the highest gain; if even the best gain is 0, refuse ("the snapshot's classes are exhausted").
- **`gain(c) = Σ weights[class]` over the classes `c` carries that nothing chosen yet covers** — a sum of CLASS weights, not the project's own gold count. That is why a one-finding project can outrank a twenty-finding one: it inherits the weight of every finding in its class, wherever they live.
- **The tie-break, in both passes: the LOWEST `project` string wins** (ascending, byte order). No decision iterates a map, so `Select` is deterministic for a fixed input; `TestSelectIsDeterministic` pins that under a pinned clock. The one refusal that reads a map — an unknown shape in the shape map — collects every invalid entry and renders them SORTED, so a shape map with two typos refuses with the same message on every run (`TestSelectRefusesTwoUnknownShapesDeterministically` pins that over eight runs).
- **The coverage arithmetic**: `covered_findings` is the sum of the covered classes' weights (the number the greedy maximised); `covered_classes` / `total_classes` count classes with `unmapped` excluded; `uncovered_classes` is sorted.
- **The hold-out rule**: `HeldOut` must name exactly two SHAPED projects, and both must appear among the picks, or `Select` refuses naming the count it picked.
