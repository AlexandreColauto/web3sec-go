## 3. What the P1 record set did not anticipate

**(1) The profile that can mint is not the profile the task named.** `host-readonly` cannot
back E4+ evidence; only `fork-runner` is in the eligible set. The task said 10a was offline and
needed "nothing but the pinned checkout and forge". It is not offline: the project's own five
tests are **fork tests** (`test/DebtManager.t.sol:51`), so reproducing them needs network, and
a networked run must be sandboxed. The container path worked first try — image present, uid
1000↔1000, container forge 1.8.1 identical to host, egress fine.

**(2) The E4+ gate models "reproduction" as a PASSING test, and this target's evidence is
negative.** Two independent rules enforce it: `ValidateExecRecord` requires
`exit_status == 0`, and `exec_output_problem` refuses any forge output showing a failing suite
— *"a failing test is not a reproduction"*. The Exactly vulnerability **is** the absence of a
guard: the fix commit's own tests fail 0/5 because `MarketNotListed` is never raised. So the
reproduction exits 1 and its suite fails, by construction, however correctly it is sandboxed.
**Absence-of-refusal evidence has no mintable path at any profile.** This is the finding that
matters, and it is not a bug in this target — it is a gap in the evidence model, which assumes
a reproduction demonstrates something happening rather than something failing to happen.

**(3) CONFIRMED is unreachable one layer earlier than the task assumed.** The task expected
the CONFIRMED *gate clause* to be the obstacle. It never ran: `HYPOTHESIS → CONFIRMED` is not
a legal edge — the path is `HYPOTHESIS → POSSIBLE → CONFIRMED` — and each hop carries an
evidence floor (`POSSIBLE` needs E2). At E0 the first hop is already refused
(`evidence level E0 < required E2 for POSSIBLE`). The transition table fires before any clause.

**(4) `FORK_RPC_URL` is not the variable this reproduction needs, and no record knows that.**
It was auto-injected as `http://host.docker.internal:8545` (a dead endpoint) and never
checked — preflight has no RPC probe. The run actually worked because the project's test reads
`vm.envString("OPTIMISM_NODE")`, which had to ride in as a plain `--env`. Every framework
diagnostic (`evidence-floor-unreachable`, the env doctor, `ContainerForkURL`) keys on
`FORK_RPC_URL` instead, so the variable that gates the checks and the variable that makes the
run work are different. The record carries both views: `environment.env_keys=["OPTIMISM_NODE"]`
against `container.env_keys=[FORK_RPC_URL, FOUNDRY_LINT_ON_BUILD, OPTIMISM_NODE]`.

**Minor.** `--workdir <host path>` bind-mounts read-write at `/wd` and is also the container
cwd; there is no container-path flag, and preflight validates only the host side, so the
profile's `filesystem: sandbox-tmp` label understates the bind. A refused mint still writes
`repro.attempt` + `repro.attempt_rolled_back` to the ledger — a refusal leaves audit residue
while the finding file stays untouched.

## 5. What this means for 10b

**10b's precondition is not met and cannot be met by re-running 10a harder.** It needs a
CONFIRMED finding; the path to CONFIRMED is blocked by (2) and (3) above as §5.1 refines
them — the binding constraint is not the E4+ gate alone — and none of that is about effort,
profile choice or RPC availability. Three honest routes, none of them taken here because
each is a decision rather than a step:

1. **Author a positive PoC** — a test asserting the drain *succeeds* against an
   attacker-supplied market. It would pass, so it would mint, and it would be a different
   artifact from the project's regression tests. This is the route that matches the gate's
   model, and it is the most work.
2. **Widen the evidence model** to admit negative evidence — a suite that fails *for the
   expected reason* is a reproduction of a defect whose signature is an absent refusal. This is
   a product change with real design weight, and it should be its own task with its own review,
   not a patch made mid-spike. This alone would not unblock CONFIRMED for this finding: §5.1
   shows the binding constraint is the E5 floor, above the gate.
3. **Use a different target for the spike** — one whose reproduction is a passing test. This
   abandons the control target's main virtue (a real, cited, on-chain incident) in exchange for
   a precondition that is already satisfied.

Until one is chosen and recorded, **10b stays blocked**, and the honest statement of Phase 2 is
that its arithmetic half is test-proven while its extraction half has no confirmed finding to
run on.

### 5.1 What actually binds CONFIRMED — and what does not

§5 above named (2) and (3) as the blockers. That is incomplete, and the exact constraint
matters, so it is recorded here as verified analysis rather than left as an impression.

**The E0/E2 floor and the E4+ gate are different constraints and must not be conflated.**
One governs the evidence floor for the `HYPOTHESIS → POSSIBLE` hop; the other governs
exec-backed E4–E6 evidence. They are separate rules with separate scope.

**E2 is obtainable without touching the E4+ gate.** `checkExecGate` only gates E4–E6
evidence, so a non-exec item at E0–E3 — for example a `reachability` or `static-analysis`
item at level E2 citing a registered artifact — bypasses the exec gate entirely, and
`POSSIBLE`'s floor is a single any-type clause that one such item satisfies. So (3)'s E0
refusal is real, but the E4+ gate is not what makes E2 unreachable.

**But there is a surface gap.** No post-filing CLI verb accepts a caller-typed E0–E3
evidence item. The four producers of `AddEvidence` are `reproduction_mint.go`,
`reachability.go` and `risk/record.go`; `reproduction.StaticReachability` mints exactly the
right E2 item and has **no CLI caller in this build**. The floor is reachable in principle
and unreachable from the command line as it stands.

**And, decisively: widening the E4+ gate to admit expected-failure evidence would NOT
unblock CONFIRMED for this finding.** The binding constraint at CONFIRMED is the **E5
floor**: `root_cause.class` is `'input-validation'`, which is not in `CLASS_CONFIRM_FLOOR`,
so `RequiredLevelFor` falls to `STATUS_FLOOR['CONFIRMED'] = E5`. That is reinforced by the
reproduction-tier clause demanding T3+, and by `evidence-floor-unreachable` demanding a fork
target. Relaxing the gate would therefore produce E4 evidence and still be refused:
`evidence level E4 < required E5 for CONFIRMED`.

Note also that the finding **does** carry `root_cause.class = 'input-validation'` — a
statement that it carries no class would be wrong.

## 5.2 The floor override binds — measured

§5.1 concluded that the binding constraint at CONFIRMED is the E5 class floor, not the E4+
pass-only gate. That conclusion rested on reading `RequiredLevelFor` and `CLASS_CONFIRM_FLOOR`;
this subsection is the measurement that decides whether the framework's own escape hatch
actually moves it. It does. **Outcome A.**

`input-validation` is unknown to the framework — absent from `CLASS_CONFIRM_FLOOR` (17
classes), from `assets/taxonomy/aliases.json` (7) and from all ten playbooks — and `bug_class`
is free-form in `assets/finding.schema.json` (`^[a-z0-9-]{3,64}$`, no enum). So the E5 is the
conservative default for an unrecognised string, not a considered judgment about absent-guard
defects. By the map's own stated principle (`levels.go:46–51` — classes whose exploitability is
"fully determined by code semantics (no dependence on live mainnet state)" are E4), an absent
validation guard belongs at E4, the rung the map already gives `access-control`,
`authorization` and `logic-error`.

**Baseline, before any change** (`webv2 brief C-725aa2c6a8`), verbatim:

```
F-cfff3ebc0250 [HYPOTHESIS E0]: evidence level E0 < required E5 for CONFIRMED
F-cfff3ebc0250 stuck at E0 (floor E5): no deployment/chain pin on the active snapshot — fork
evidence (E5+) has no fork target, for single-call PoCs and multi-tx sequence PoCs
(`webv2 sequence run`) alike; pin one (`webv2 snap`) or record a floor override
(`webv2 floors set`); FORK_RPC_URL is not set — the fork-runner profile cannot reach a chain
```

**The override**, recorded with actor and a general reason rather than one naming this target:

```
webv2 floors C-725aa2c6a8 set input-validation E4 --actor xand --reason 'absent-guard defect
classes are fully determined by code semantics (levels.go:46-51); input-validation is absent
from CLASS_CONFIRM_FLOOR, so RequiredLevelFor falls to STATUS_FLOOR["CONFIRMED"]=E5 — the
conservative default for an unknown class string, not a judgment about this class. Set to E4
for this campaign, matching access-control/authorization/logic-error.'
floor policy set: input-validation -> E4 (actor xand, 2026-09-22T16:50:00.156207+00:00)
```

The advisory on stderr was expected and correct, and was not "fixed":

```
note: input-validation is not a known taxonomy class — this floor binds nothing until a
finding carries it (open vocabulary is legal, typos are not free)
```

It binds because the finding does carry the class.

**Post-override**, same verb, verbatim:

```
F-cfff3ebc0250 [HYPOTHESIS E0]: evidence level E0 < required E4 for CONFIRMED
```

The required level moved **E5 → E4**, and the "stuck at E0 (floor E5) / no fork target" line
disappeared with it: with the floor at E4 the finding is no longer structurally dependent on a
fork target. **The override binds on this path.**

**The mint was re-attempted and refused again — now for the other reason.** On the
profile-correct container exec `EXEC-54b9b316c6`:

```
mint failed: exec EXEC-54b9b316c6 exited with status 1; a run that did not succeed is not a
reproduction — fix the PoC and re-run before minting evidence
```

That is the E4-level refusal, and it is the point of this measurement: the floor was the
*binding* constraint and the override lifted it, so what remains is the exec gate's pass-only
model. **The override makes the expected-outcome work sufficient; it does not replace it.**

**Audit** — `webv2 audit C-725aa2c6a8` → `audit FAIL`, fifteen sections at 0 problems
including **`floor_policy=0 problem(s)`**, and one problem elsewhere:

```
regression_suite=1 problem(s)
```

The override is therefore reconciled as a recorded, attributed decision and is **not** flagged
as a hand-edit. The remaining problem is §4's missing P1 handoff, unrelated to this task.

**Left set, deliberately.** The override is a general, argued judgment rather than a
target-specific convenience; it is audit-reconciled; it is the precondition §5.1 identified for
the expected-outcome work; and unsetting it would immediately restore a diagnosis that has been
made and answered. It binds only for findings carrying `input-validation` in this one campaign,
and it is one command to reverse:

```
webv2 floors C-725aa2c6a8 unset input-validation --actor <you> --reason <why>
```

**One discrepancy from the task's stated expectation, recorded rather than smoothed over.** The
baseline was expected to read `evidence level E4 < required E5 for CONFIRMED`; it reads
**`E0 < required E5`**. The difference is not a wrong premise — the load-bearing claim, that
the CONFIRMED floor is E5 for this class and binds, is confirmed verbatim. It is that the E4 in
the expected string was the level the mint *would* have produced had it succeeded, and the mint
was refused, so the finding still carries no evidence and sits at E0. The measurement is
unaffected: the required level is what the override moves, and it moved.
