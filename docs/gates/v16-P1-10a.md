## 3. What the P1 record set did not anticipate

**(1) The profile that can mint is not the profile the task named.** `host-readonly` cannot
back E4+ evidence; only `fork-runner` is in the eligible set. The task said 10a was offline and
needed "nothing but the pinned checkout and forge". It is not offline: the project's own five
tests are **fork tests** (`test/DebtManager.t.sol:51`), so reproducing them needs network, and
a networked run must be sandboxed. The container path worked first try — image present, uid
1000↔1000, container forge 1.8.1 identical to host, egress fine.

**(2) The E4+ gate models "reproduction" as a PASSING test, and this target's evidence is
negative.** Two independent rules enforce it: `ValidateExecRecord` requires
`exit_status == 0`, and `exec_output_problem` refuses any forge output showing a failing suite
— *"a failing test is not a reproduction"*. The Exactly vulnerability **is** the absence of a
guard: the fix commit's own tests fail 0/5 because `MarketNotListed` is never raised. So the
reproduction exits 1 and its suite fails, by construction, however correctly it is sandboxed.
**Absence-of-refusal evidence has no mintable path at any profile.** This is the finding that
matters, and it is not a bug in this target — it is a gap in the evidence model, which assumes
a reproduction demonstrates something happening rather than something failing to happen.

**(3) CONFIRMED is unreachable one layer earlier than the task assumed.** The task expected
the CONFIRMED *gate clause* to be the obstacle. It never ran: `HYPOTHESIS → CONFIRMED` is not
a legal edge — the path is `HYPOTHESIS → POSSIBLE → CONFIRMED` — and each hop carries an
evidence floor (`POSSIBLE` needs E2). At E0 the first hop is already refused
(`evidence level E0 < required E2 for POSSIBLE`). The transition table fires before any clause.

**(4) `FORK_RPC_URL` is not the variable this reproduction needs, and no record knows that.**
It was auto-injected as `http://host.docker.internal:8545` (a dead endpoint) and never
checked — preflight has no RPC probe. The run actually worked because the project's test reads
`vm.envString("OPTIMISM_NODE")`, which had to ride in as a plain `--env`. Every framework
diagnostic (`evidence-floor-unreachable`, the env doctor, `ContainerForkURL`) keys on
`FORK_RPC_URL` instead, so the variable that gates the checks and the variable that makes the
run work are different. The record carries both views: `environment.env_keys=["OPTIMISM_NODE"]`
against `container.env_keys=[FORK_RPC_URL, FOUNDRY_LINT_ON_BUILD, OPTIMISM_NODE]`.

**Minor.** `--workdir <host path>` bind-mounts read-write at `/wd` and is also the container
cwd; there is no container-path flag, and preflight validates only the host side, so the
profile's `filesystem: sandbox-tmp` label understates the bind. A refused mint still writes
`repro.attempt` + `repro.attempt_rolled_back` to the ledger — a refusal leaves audit residue
while the finding file stays untouched.

## 5. What this means for 10b

**10b's precondition is not met and cannot be met by re-running 10a harder.** It needs a
CONFIRMED finding; the path to CONFIRMED is blocked by (2) and (3) above as §5.1 refines
them — the binding constraint is not the E4+ gate alone — and none of that is about effort,
profile choice or RPC availability. Three honest routes, none of them taken here because
each is a decision rather than a step:

1. **Author a positive PoC** — a test asserting the drain *succeeds* against an
   attacker-supplied market. It would pass, so it would mint, and it would be a different
   artifact from the project's regression tests. This is the route that matches the gate's
   model, and it is the most work.
2. **Widen the evidence model** to admit negative evidence — a suite that fails *for the
   expected reason* is a reproduction of a defect whose signature is an absent refusal. This is
   a product change with real design weight, and it should be its own task with its own review,
   not a patch made mid-spike. This alone would not unblock CONFIRMED for this finding: §5.1
   shows the binding constraint is the E5 floor, above the gate.
3. **Use a different target for the spike** — one whose reproduction is a passing test. This
   abandons the control target's main virtue (a real, cited, on-chain incident) in exchange for
   a precondition that is already satisfied.

Until one is chosen and recorded, **10b stays blocked**, and the honest statement of Phase 2 is
that its arithmetic half is test-proven while its extraction half has no confirmed finding to
run on.

### 5.1 What actually binds CONFIRMED — and what does not

§5 above named (2) and (3) as the blockers. That is incomplete, and the exact constraint
matters, so it is recorded here as verified analysis rather than left as an impression.

**The E0/E2 floor and the E4+ gate are different constraints and must not be conflated.**
One governs the evidence floor for the `HYPOTHESIS → POSSIBLE` hop; the other governs
exec-backed E4–E6 evidence. They are separate rules with separate scope.

**E2 is obtainable without touching the E4+ gate.** `checkExecGate` only gates E4–E6
evidence, so a non-exec item at E0–E3 — for example a `reachability` or `static-analysis`
item at level E2 citing a registered artifact — bypasses the exec gate entirely, and
`POSSIBLE`'s floor is a single any-type clause that one such item satisfies. So (3)'s E0
refusal is real, but the E4+ gate is not what makes E2 unreachable.

**But there is a surface gap.** No post-filing CLI verb accepts a caller-typed E0–E3
evidence item. The four producers of `AddEvidence` are `reproduction_mint.go`,
`reachability.go` and `risk/record.go`; `reproduction.StaticReachability` mints exactly the
right E2 item and has **no CLI caller in this build**. The floor is reachable in principle
and unreachable from the command line as it stands.

**And, decisively: widening the E4+ gate to admit expected-failure evidence would NOT
unblock CONFIRMED for this finding.** The binding constraint at CONFIRMED is the **E5
floor**: `root_cause.class` is `'input-validation'`, which is not in `CLASS_CONFIRM_FLOOR`,
so `RequiredLevelFor` falls to `STATUS_FLOOR['CONFIRMED'] = E5`. That is reinforced by the
reproduction-tier clause demanding T3+, and by `evidence-floor-unreachable` demanding a fork
target. Relaxing the gate would therefore produce E4 evidence and still be refused:
`evidence level E4 < required E5 for CONFIRMED`.

Note also that the finding **does** carry `root_cause.class = 'input-validation'` — a
statement that it carries no class would be wrong.

### Phase 2: the design

**The defect.** The gate treats "reproduction" as *a passing test suite* — `exit_status` must
be 0 (`internal/findings/exec_evidence.go:158`) and a suite showing `[FAIL]` is rejected
(`internal/sandbox/sandbox.go:135`). For an absent guard the honest reproduction exits non-zero
with a failing suite *by construction*, so absence-of-refusal evidence has no mintable path at
any profile. This is not a fact about one target: it is the whole **absent-guard family** —
missing access control, missing validation, missing reentrancy guard. For every one of them the
evidence is that a guard which should have refused did not, and a gate that can only certify a
green suite structurally cannot certify any of them.

**The shape.** The gate already encodes an expectation; it hardcodes `expected = pass`. Make it
explicit on the record and compare. But polarity alone is not enough, and this is where I would
extend the sketch: `expected_outcome: fail` is satisfied by a typo, a missing dependency or a
compile error just as well as by an absent guard. So the design carries **two** keys, and the
second is what makes the claim falsifiable:

- `expected_outcome` — `"pass"` or `"fail"`. **Absent means `"pass"`**, so every existing record
  keeps its exact bytes and its exact semantics.
- `expected_failure` — required when `expected_outcome` is `"fail"`, forbidden otherwise. A
  short signature the operator commits to *before the run*, which the gate asserts appears in
  the captured output.

That last check is the integrity condition. It does not make the claim true, but it makes it
mechanical and falsifiable, and it forces the expectation to be stated in advance.

**Where it lives.** `assets/schema/sandbox_execution.schema.json` — a new optional
`expected_outcome` (enum, `additionalProperties: false` is already set) and a new optional
`expected_failure`. The write path already enforces the schema: `register_exec.go:149` calls
`validation.WriteJson(..., "sandbox_execution")`, so the schema edit is the enforcement, with
no extra `validation.Validate` call needed.

**The predicate changes, exactly.**

1. `internal/findings/exec_evidence.go:158` — `ValidateExecRecord`. Replace the hard
   `exit.I == 0` test with a comparison against the record's declared expectation: under
   `pass`, exit must be 0 (today's rule, unchanged); under `fail`, exit must be **non-zero**,
   and `expected_failure` must be present and must occur in `sandbox.ExecOutput(rec)`. The
   refusal text for a `fail` record that exited 0 needs a new string (below).
2. `internal/sandbox/sandbox.go:135` — `ExecOutputProblem`'s forge branch. The
   `s.HasFailMarker || *s.Failed > 0` refusal becomes conditional on the expectation: under
   `pass` it refuses as today; under `fail` a failing suite is the *expected* shape, and the
   `NoTests` and no-counters branches still refuse unconditionally (a run that matched nothing
   proves nothing under either expectation).

**Ledger law.** No new event, and no projection change: the field is part of the exec record
written once at registration, and `register_exec.go` already appends exactly one hash-chained
event per exec. **The integrity condition is that the expectation must be declared at exec
time, before the run** — a `--expect` accepted at *mint* time would let an operator write the
expectation after seeing the result, which is the failure mode this whole design exists to
close. That is also the argument for putting the field on the exec record rather than on the
evidence item.

**Byte-pinned CLI surfaces — two, and they must change together.**

- `internal/cli/cmd_exec.go:58` (`execHelp`, "argparse's output, byte-exact") gains:
  ```
    --expect {pass,fail}  what this run must do to count as a reproduction (default:
                       pass — a passing suite). Declared BEFORE the run and recorded
                       on the EXEC ledger; an absent-guard defect is evidenced by the
                       expected refusal NOT happening, which fails by construction
    --expect-failure TEXT  with --expect fail: the failure signature the run must show,
                       asserted to appear in the captured output (required, and refused
                       under --expect pass)
  ```
- `internal/cli/cmd_dedup.go:153` (the usage map) gains the same two options, re-wrapped to
  that map's 80-column style.

`help_test.go` pins help output, so both changes land with their pinned-test updates in the
same commit.

**Determinism pins.** None needed: the field is an operator literal, and no `time.Now()` or
UUID enters the record.

**Test plan** — plain Go tests, same package, `t.TempDir()`, no Docker/network/model:

- `ValidateExecRecord`, table-driven: `pass`+exit0+green → accept; `pass`+exit1 → refuse;
  `fail`+exit1+signature-present → **accept**; `fail`+exit0 → refuse; `fail`+exit1+signature
  absent → refuse; `fail` with no `expected_failure` → refuse; `expected_failure` under `pass`
  → refuse.
- `ExecOutputProblem`: `[FAIL]` suite under `fail` → nil; under `pass` → problem; `NoTests`
  under both → problem.
- Schema: a record carrying both keys validates; a bad enum value and an `expected_failure`
  under `pass` both fail validation.
- **The backward-compatibility test is the load-bearing one:** a record with no
  `expected_outcome` must behave *exactly* as today, byte-for-byte in its refusals.
- Then `go test ./... -count=1`, then `scripts/verify-full.sh`.

**`poc-tier` / `type` semantics do not change.** `MintEvidenceLevelType` still assigns E4, or
E5 for T3/T4 claims; `unit-test` remains the honest type. The expectation describes *what was
expected*, the type describes *how it was checked* — keeping them orthogonal avoids a
combinatorial enum. A new `type` member would be the wrong axis.

**Two open decisions this design needs from you** (not resolvable from the code):

1. **Should `expected_failure` be required?** I say yes — without it the design admits "it
   failed, I promise it was for the right reason", which is the defect wearing a new key. But
   it is a real CLI-surface increase and a judgment about how much ceremony evidence needs.
2. **How strict should the signature check be?** "Occurs anywhere in the captured output" is
   simple and hard to game only in the sense that it must be stated in advance. Requiring it
   to occur on a `[FAIL:` line is stronger but forge-format-specific, and `ExecOutputProblem`
   already treats non-forge commands as out of scope — so the strict version would only apply
   to forge runs, leaving other harnesses on the weaker rule.

## 5.4 Route 2 landed — the mint admits an absent-guard reproduction

§5.3 designed the change and left two decisions open. Both were resolved in favour of the
stricter option, and the change is implemented.

### The admission rule, as built

Two keys on the **exec record** (not the evidence item — declaring the expectation at mint time
would be writing it after seeing the result):

- `expected_outcome` — `pass` | `fail`. **Absent means `pass`**, so every pre-existing record
  keeps its exact bytes and its exact behaviour. This is the load-bearing backward-compat
  property and it is tested directly.
- `expected_failure` — the declared signature. **Required** under `fail`, **forbidden** under
  `pass` (a declared failure signature on a run expected to pass is a contradiction, and is
  refused rather than ignored).

Under `fail`, a record is admitted only when all three hold:

1. `exit_status` is **non-zero**.
2. the signature appears on a line that also carries a **real per-test failure marker** —
   for a forge-like command the token `[FAIL` (bracket then FAIL, with the separator that
   follows deliberately *not* pinned: forge renders `[FAIL: …]` and `[FAIL. Reason: …]`
   across versions), and for any other harness the plain substring `FAIL`, no better marker
   existing for an arbitrary command. The signature must also clear a **specificity floor**:
   at least 8 characters after trimming, and never the literal `FAIL`;
3. `sandbox.ClassifyFailure(rec)` reports class **`logic`**. Infrastructure causes
   (`environment`, `setup`, `unknown`, `none`) are refused even when the signature matches, so
   the classifier stays the single authority on whether the run was a real test failure.

**No speculative escape hatch was built.** If a real case appears where no signature can be
named, it mirrors the `unpriceable` idiom as a named, attributed decision — built then, not now.

### The third touch point the design missed

`verifyExecReference` (`internal/findings/ingest_evidence_gate.go:113`) runs *after* mint's own
gate on every mint path and carried its own "must cite a run that succeeded" check. Without a
branch there, an admitted expected-failure record still died on that check and the new rule
would have had no end-to-end path. The branch defers the whole `fail` case to
`ValidateExecRecord` — one function, one opinion, rather than a second forked rule — and the
`pass` trio keeps its bytes. This is a deviation from the design's touch-point table, and it was
necessary.

### The measurement

Two fresh `fork-runner` execs, since `EXEC-54b9b316c6` predates the field and therefore reads as
`pass` — it cannot demonstrate admission, and a record cannot gain the fail path's privileges
without declaring them.

The first attempt, `EXEC-111317493e`, declared `expected_failure: MarketNotListed` and was
**refused**:

```
mint failed: exec EXEC-111317493e: expected_failure 'MarketNotListed' does not appear on any
captured line containing the substring FAIL — the declared failure signature must be seen on a
failing line of the captured output (declared before the run, checked now)
```

That refusal is the mechanism working, and it caught something real. The same command, workdir,
image and fork block as the earlier runs produced a **different failure**:

| exec | `testFakeMarketCrossDeleverage` | gas |
|---|---|---|
| `EXEC-54b9b316c6` (earlier) | `[FAIL: Error != expected error: AS != MarketNotListed()]` | 2,255,374 |
| `EXEC-111317493e` (fresh) | `[FAIL: EvmError: Revert]` | 70,178 |

Same block `99811375`, same `OPTIMISM_NODE` key, no local fork RPC listening on 8545. The other
four tests are byte-identical between the runs; only the first diverges, and only in how its
revert is rendered. So a signature naming the *assertion* outcome is unstable across runs of an
identical command, while one naming the *observed refusal* is not — which is precisely why the
signature must be committed before the run rather than chosen from the output afterwards.

The second attempt, `EXEC-5709ef04f2`, declared the stable signature
`call reverted as expected, but without data` (present on four of the five `[FAIL: …]` lines in
both runs) and was **admitted**:

```
F-cfff3ebc0250: minted unit-test evidence from EXEC-5709ef04f2 — level E4
```

`EV-336724ba` is the item: level **E4**, type `unit-test`. The finding's status remains
`HYPOTHESIS` — per §5.3's scope this task stops at "the mint admits" and does not drive the
finding to CONFIRMED.

### Gates

- `go test ./... -count=1` — **72 packages ok, zero failures** (run with `-p 2` to bound memory;
  the naive parallel invocation is what has OOM'd this box before).
- `scripts/verify-full.sh` — see the commit message.
- `golangci-lint run --new-from-rev HEAD` over the four touched packages — clean.
- Focused packages run individually with `-p 1`: sandbox, findings, cli, reproduction — all ok.

**Mutation-checked.** Making `ExecExpectedOutcome` return `pass` unconditionally fails three
sandbox tests plus the findings admission tests; dropping the `FAIL`-line requirement from
`failureSignatureOnFailLine` fails the admission cases that exist to pin it. Both were asserted
to have landed before the result was trusted.

**`poc-tier` and `type` semantics did not move.** `MintEvidenceLevelType` is untouched and
`unit-test` remains the honest type — the expectation describes *what was expected*, the type
describes *how it was checked*. No new ledger event: the field rides the record written once at
registration, which already appends exactly one hash-chained event.

`CLASS_CONFIRM_FLOOR` and `STATUS_FLOOR` are untouched; the per-campaign override recorded in
§5.2 remains the answer to the floor.

### 5.4.1 The adversarial review, and what it broke

The landed change was reviewed adversarially by a second model against the seven claims §5.4
makes. Six were confirmed — backward compatibility byte-for-byte (including a re-measurement
against the pre-commit message), the schema's `allOf`/`if`/`then` conditionals actually being
enforced by the validator rather than decorative, the CLI refusing a contradictory invocation
*before* the container starts, the truncation and empty-output checks still applying on the
fail path, no new ledger event, and `poc-tier`/`type` unmoved. The `verifyExecReference`
deferral was examined check by check and opens no hole: the trio's three checks are all
re-covered by `ValidateExecRecord`, and the record-existence, profile-equality and
finding-match checks all run *before* the branch.

**One claim was refuted, and it was the important one.**

The rule as first written admitted any line containing the substring `FAIL`. Measured through
the real `ValidateExecRecord`, these signatures were all **admitted** on a suite that
reproduced nothing:

| declared signature | first rule | corrected rule |
|---|---|---|
| `FAIL` | admitted | refused — literal `FAIL` is a tautology |
| `a` | admitted | refused — below the specificity floor |
| `test` | admitted | refused — below the specificity floor |
| `Suite result` | **admitted** | refused — not a per-test failure line |

`Suite result` is the damning one: forge's summary line reads
`Suite result: FAILED. 0 passed; 5 failed; …`, which contains `FAIL`, so the *summary* satisfied
a check meant to identify a per-test failure. The design's whole integrity argument — that the
operator commits to a falsifiable signature before the run — held only if the operator chose to
be specific. Nothing enforced it, which is the same shape as the defect this change exists to
close.

The correction has two parts, and the second is a deliberate narrowing of §5.4's rule:

- a **specificity floor**: at least 8 characters after trimming, and never the literal `FAIL`
  (enforced in the schema's `minLength` *and* in Go, so the Go check does not depend on the
  schema being the only line);
- for a **forge-like** command the line must carry the token `[FAIL` — bracket then `FAIL`,
  with the separator that follows left unpinned. §5.4 rejected a `[FAIL:` prefix because forge's
  punctuation drifts between versions; `[FAIL` keeps that anti-brittleness while excluding the
  suite-summary line, which was the actual hole. Non-forge harnesses keep the plain `FAIL`
  substring, no better marker existing for an arbitrary command.

The line classification moved into `internal/sandbox` as `FailureSignatureOnFailLine`, so forge
knowledge stays beside the unexported `commandIsForgeLike` rather than being duplicated.

Two smaller defects were also fixed: under `expected_outcome: fail` a capture with `[FAIL]`
markers but no parsed counters was refused with *"cannot verify a test actually ran and passed"*
— the wrong polarity, asking an expected-failure run for a PASS marker it must never produce;
and two tests lacked teeth, one of them inspecting only the final record so that a regression
stamping the expectation *after* the payload ran would still have passed. Both were replaced
with assertions proven able to fail.

**Recorded and deliberately not fixed:** the expectation keys live only in the mutable
`exec_record.json` and are not anchored in the hash-chained `sandbox.exec` event, which carries
only `profile`, `exit` and `finding`. So a post-hoc edit that stamps `expected_outcome: fail`
after seeing the output is indistinguishable from an exec-time declaration — the integrity
condition §5.3 rests on is *stated* but not *enforced*. The honest fix anchors the whole record,
not two keys (the same weakness already applies to `exit_status`), so it is scoped separately
rather than half-done here.
